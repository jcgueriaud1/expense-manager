# ADR-0016 — Persistence baseline: bigint PKs, app-side audit timestamps, minimal V1

**Status:** Accepted

## Context
Phase 0's Flyway baseline (plan 0.6) asked whether `V1__init.sql` should be
empty or carry cross-cutting scaffolding, which forced three coupled decisions:
primary-key strategy, where audit timestamps are set, and therefore what (if
anything) is genuinely shared DB machinery worth planting up front.

## Decision
- **Primary keys: `bigint` identity** (`GENERATED BY DEFAULT AS IDENTITY`) on all
  tables. No UUIDs in V1.
- **Audit timestamps: app-side, Hibernate-specific** — `@CreationTimestamp` /
  `@UpdateTimestamp` on entity fields. **No DB triggers.** Timestamps only
  (`createdAt` / `updatedAt`); **no `@CreatedBy`/`@LastModifiedBy` audit-user
  tracking** — attribution (report owner, approver) is modelled as explicit
  domain fields where the domain needs it, not audit infrastructure.
- **`V1__init.sql` is therefore a near-empty baseline** whose job is to prove
  Flyway wires up and runs on startup. No extensions (`pgcrypto`, `citext`) are
  planted speculatively; each feature phase adds its own `V2__…`, `V3__…`
  migration for its tables.

## Consequences
- Lowest-ceremony choice for a JPA-centric app; no trigger/entity in-memory
  staleness trap, no extension maintenance.
- **`bigint` PKs are sequential and guessable.** Report-detail routes (UC-005)
  carry the ID in the URL, so unauthorized access is prevented by ADR-0008
  method/route security on every access — enumeration without authorization
  yields nothing. Accepted trade-off for an internal tool; UUIDs would be
  defense-in-depth we don't need here.
- A shared `@MappedSuperclass` (e.g. `base.AuditedEntity`) carries the two
  timestamp fields so every entity inherits them; this is Java-side, not V1 SQL.
- Chose Hibernate annotations over Spring Data JPA auditing deliberately: Spring
  Data would add created-by/modified-by via `AuditorAware`, but we don't want
  audit-user tracking, so its extra setup buys nothing here.
